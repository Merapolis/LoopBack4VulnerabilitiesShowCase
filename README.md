# LoopBack 4 Oracle Lab

A minimal LoopBack 4 + TypeScript application used as a controlled lab for a
blog write-up. This repository contains the **secure baseline**: a small
document domain backed by LoopBack's in-memory connector, with read-only
endpoints and deliberate, well-defined visibility rules.

- **Node.js:** 22 (see `.nvmrc`)
- **npm:** use the version bundled with Node 22; no global installs required

## Setup and commands

```sh
npm ci          # install exact dependencies from package-lock.json
npm run build   # compile TypeScript (tsc) into dist/
npm test        # build, then run the node:test suite
npm start       # run the compiled application
```

The server listens on **http://127.0.0.1:3000 only** — it is bound to the
loopback interface and is not reachable from the network.

## Endpoints

| Method | Path                    | Description                                    |
|--------|-------------------------|-----------------------------------------------|
| GET    | `/ping`                 | Health check, returns `{"status":"ok"}`      |
| GET    | `/documents`            | Documents visible to the selected fixture actor |
| GET    | `/documents/{id}`       | A single document by generated id               |
| GET    | `/documents/search?title=...` | Exact-title search within visibility scope |

Example requests:

```sh
curl http://127.0.0.1:3000/ping
curl http://127.0.0.1:3000/documents
curl -H "X-Demo-User: alice" http://127.0.0.1:3000/documents
curl -H "X-Demo-User: bob" http://127.0.0.1:3000/documents/1
curl -H "X-Demo-User: alice" "http://127.0.0.1:3000/documents/search?title=Alice%20Private"
```

## X-Demo-User is NOT authentication

The `X-Demo-User` header accepts only the values `alice` or `bob`. It is a
**synthetic actor selector for the lab fixtures** — a stand-in that lets a
request identify *which fixture persona* it is acting as. It is **explicitly
not an authentication mechanism**: it provides no credentials, no verification,
and no security guarantees. Any other value is rejected with `400 Bad Request`.

## Seeded records (all fictional)

The application idempotently seeds three obviously synthetic documents at
startup (ids are generated by the connector; shown here as created):

| Title           | Owner   | Visibility | Content        |
|-----------------|---------|------------|----------------|
| Public Document | alice   | public     | Public content |
| Alice Private   | alice   | private    | Alice secret   |
| Bob Private     | bob     | private    | Bob secret     |

**All values are fictional** demo data. They are not secrets, credentials, or
real records of any kind.

## Secure-baseline behavior

- `GET /documents` returns all public documents plus the private documents
  owned by the selected fixture actor (or public documents only when no actor
  is selected).
- `GET /documents/{id}` returns a document only when it is public or owned by
  the selected actor.
- `GET /documents/search?title=...` performs **exact title matching** within
  the same visibility/ownership scope. No wildcard, LIKE/NLIKE, regular
  expression, or raw LoopBack filter syntax is accepted from HTTP requests.
- **Inaccessible and nonexistent documents are intentionally
  indistinguishable**: both produce an identical `404 Not Found` response with
  the same status code, body, and error message. The baseline does not leak
  the existence of documents the actor may not access.

## Scope notes

- The intentional **oracle vulnerability demonstration is NOT part of this
  baseline**. It will be introduced later as an explicitly isolated branch or
  change; do not expect it here.
- This is a **local test application, not a production template**: the
  in-memory datasource resets on restart, `X-Demo-User` is not authentication,
  and the server binds only to 127.0.0.1.
